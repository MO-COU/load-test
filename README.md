# 선착순 쿠폰 발급 — 동시성 제어 6가지 비교

재고 10,000장에 회원 20,000명이 동시에 몰리는 상황을 6가지 방식으로 구현하고
같은 조건에서 측정했다. `main` 은 동시성 제어가 없는 baseline 이고,
각 방식은 `exp/*` 브랜치에 있다.

## 1. 실험 목적

동시성 제어를 **DB 에서 하느냐 인메모리에서 하느냐**가 성능을 가르는지 확인한다.
가른다면 락 경합이 커넥션 풀·워커 스레드 고갈로 이어지는 경로를 지표로 확인한다.

## 2. 비교 대상

동시성 제어 전략은 셋뿐이고, 각각을 DB 와 Redis 로 구현한 3쌍이다.

| 전략 | DB | Redis |
|---|---|---|
| **대기** 락을 걸고 시작 | `pessimistic-lock` | `redisson-rlock` |
| **재시도** 충돌하면 다시 | `optimistic` | `redis-watch` |
| **원자적** 한 번에 처리 | `atomic-update` | `redis-lua` |

`redisson-rlock` 은 락만 Redis 이고 재고 판정은 DB 에서 한다.
"Redis 를 썼기 때문"과 "판정을 옮겼기 때문"을 가르는 반례다.

## 3. 정합성 검증

성능을 재기 전에 통과해야 한다. 틀린 구현은 아무리 빨라도 비교 대상이 아니다.

| 검증 | 방법 | `exp/*` 6개 | `main` |
|---|---|---|---|
| 초과 발급 | 회원 2,000명이 재고 1,000장에 동시 요청 | 통과 | **2,000장 발급 (2배)** |
| 중복 발급 | 같은 회원으로 스레드 100개가 동시 출발 | 통과 | 통과 |
| Redis 보상 | 재고·발급자 명단이 DB 기록과 일치 | `lua`·`watch` 통과 | 해당 없음 |

`main` 이 중복 발급을 막는 것은 `(coupon_id, member_id)` UNIQUE 제약 덕분이다.
**락이 필요한 것은 재고 초과 하나**다.

HTTP 를 거치지 않는 JUnit 통합 테스트로 검증한다. 소켓·OS·Tomcat 계층이
결과에 섞이지 않고 호출 수가 결정적이기 때문이다. `main` 에서 `./gradlew test` 를 돌리면
초과 발급 테스트가 실패한다. 동시성 제어가 없는 baseline 이라 정상이다.

## 4. 부하 테스트

부하 생성기와 애플리케이션이 CPU 를 나눠 쓰면 처리량을 믿을 수 없어 EC2 2대로 나눴다.

```
┌──────────────┐               ┌───────────────────────┐
│  k6 server   │  ---load--->  │  app + MySQL + Redis  │
│ c5.4xlarge   │               │      c5.2xlarge       │
└──────────────┘               └───────────────────────┘
```

```
부하    회원 20,000명이 1인 1요청으로 동시 출발 (k6 per-vu-iterations)
        재요청하지 않는다 — 요청 수를 20,000 으로 고정해야 방식 간 부하가 같아진다
재고    10,000장 — 회원이 재고보다 많아 품절·중복이 발생한다
자원    커넥션 풀 16 · 워커 스레드 200 · accept-count 32768
재시도  서버가 최대 5회 시도, 실패마다 5~19ms 랜덤 백오프 (optimistic, redis-watch)
타임아웃 요청 60초 (k6 기본값). 넘기면 사용자는 결과를 받지 못한 것으로 센다
```

커넥션 풀 16 은 vCPU 8 × 2 로 정한 값이다. HikariCP 권장식 `(코어 수 × 2) + 디스크 수` 의
코어 수는 물리 코어 기준이라(c5.2xlarge 4코어) 식대로라면 8-9 다. 풀 9 로 잰 결과는 [5.1](#51-커넥션-풀-9) 에 있다.
`accept-count` 는 2만 개가 한꺼번에 도착할 때 기본값 100 으로는 연결이 버려지므로
크게 잡았다.

부하 생성기가 측정 대상보다 먼저 지치면 "서버가 느린 것"과 "부하를 못 만든 것"을
구분할 수 없다. 그래서 k6 서버를 한 단계 크게 잡았다. k6 쪽은 VU 20,000 을 만드는 데
필요한 메모리(VU 당 1-5MB)가 실제 제약이었고, 앱 서버는 그보다 한 단계 아래로 정했다.
앱 서버의 부하 구간 CPU 는 [6.4](#64-부하-구간-cpu) 에 있다.
C 시리즈는 CPU 성능이 일정해서 골랐다 — 버스터블(T) 계열은 크레딧이 소진되면
성능이 떨어져 측정 중 조건이 변한다.

발급 1건이 DB 에 남기는 것은 둘이다.

```
coupon_issue INSERT          회원마다 다른 행이라 경합하지 않는다
coupon.issued_count UPDATE   같은 행이라 여기서 직렬화된다
                             (재고 판정을 Redis 가 하는 방식은 이 카운터를 갱신하지 않는다)
```

두 번째가 행 락 대기의 원인이다.

수집은 네 곳에서 했다.

| 출처 | 무엇을 말해주는가 |
|---|---|
| k6 요약 | 소요 시간·발급 건수·실패율과 그 구성(5xx·타임아웃) |
| Actuator (0.2초 간격) | 커넥션 풀과 워커 스레드가 실제로 포화됐는지 |
| MySQL·Redis 전역 상태 | 락 대기, 실행된 쿼리·명령 수 |
| vmstat (1초 간격) | 부하가 걸린 구간의 CPU 사용률 |

측정 서버는 [`infra/`](infra) 의 Terraform 으로 측정 전용으로 띄우고 끝나면 지웠다.
통일 조건(풀 16, accept-count 32768 등)은 환경변수로 넣었다.

절차와 재현 방법은 [CONTRIBUTING.md](CONTRIBUTING.md) 에 있다.

2026-11-05 측정. 브랜치당 2회, 아래는 2회의 범위다. 모든 방식이 정확히 20,000 요청을 받았다.

|---|---|---:|---:|---:|---:|---:|---:|---:|
| `redis-lua` | 인메모리 | **12.0초** | 10,000 완판 | **0%** | 0 | 0 | 11.2-11.4s | 184 |
| `redis-watch` | 인메모리 | 18.6-18.7초 | **1,475-1,526 미소진** | **92.4-92.6%** | 18,474-18,525 | 0 | 17.7s | 0 |
| `atomic-update` | DB | 60초+ ⏱ | 10,000 완판 | 57.0-57.6% | 0 | 11,406-11,522 | 59.9s ⏱ | 184 |
| `pessimistic-lock` | DB | 60초+ ⏱ | 10,000 완판 | 59.9-60.4% | 0 | 11,972-12,080 | 59.9s ⏱ | 184 |
| `redisson-rlock` | DB | 60초+ ⏱ | 10,000 완판 | 67.8-68.0% | 0 | 13,566-13,594 | 59.9s ⏱ | 0 (active 1) |
| `optimistic` | DB | 60초+ ⏱ | **5,546-5,552 미소진** | 77.0% | 11,895-11,937 | 3,461-3,513 | 59.9s ⏱ | 181 |

- **소요 시간** — k6 가 2만 이터레이션을 끝낸 시각. `60초+ ⏱` 는 요청 타임아웃에
  걸려 잘린 값으로, 실제로는 그 이상 걸렸다.
- **실패율** — `200`·`409` 를 받지 못한 요청의 비율. 재요청하지 않으므로 한 번 눌러서
  답을 받았는가를 그대로 나타낸다. 5xx 와 60초 타임아웃으로 나눠 셌다.
  - 행 락·분산락 세 방식의 실패는 전부 타임아웃이다. 커넥션 대기 상한(10초)에 걸린 5xx 는 없었다.
    워커 스레드 200개가 찬 동안 나머지 요청은 그 앞에서 차례를 기다리다 60초에 잘렸다
    (커널 accept 큐 최대 7,951-14,155).
  - `redis-watch` 의 실패는 전부 5xx 다(5xx 까지 걸린 시간 중앙값 11.4-11.5초).
    `optimistic` 은 5xx(중앙값 32.5-32.7초)와 타임아웃이 섞였다.
- **DB 발급** — k6 가 포기한 뒤에도 서버가 처리를 끝내므로, 서버가 밀린 요청을
  다 소화한 뒤 세었다.
- 풀 9 를 포함한 20회 전부 초과 발급 0 · 중복 발급 0.

2026-08-31 측정과 비교하면 순위와 완판 여부는 같고, 실패율은 2회 평균으로 0-4%p 높다
(`lua` 0, `watch` +1.0, `optimistic` +1.6, `atomic` +3.5, `redisson` +3.5, `pessimistic` +3.9).
방식별 상세 수치, 회차별 값, 이전 측정은 [docs/results.md](docs/results.md) 에,
원자료는 [results](results) 에 있다.

### 5.1 커넥션 풀 9

DB 판정 4방식을 권장식 값인 풀 9 로도 2회씩 쟀다. 같은 서버에서 16 → 9 → 16 → 9 순으로 번갈아 돌렸다.

| 방식 | 실패율 (풀 16) | 실패율 (풀 9) | DB 발급 (풀 16) | DB 발급 (풀 9) | 락 대기 (풀 16) | 락 대기 (풀 9) |
|---|---:|---:|---:|---:|---:|---:|
| `atomic-update` | 57.0-57.6% | 57.4-58.1% | 10,000 | 10,000 | 19,999 | 19,999 |
| `pessimistic-lock` | 59.9-60.4% | 60.7-61.3% | 10,000 | 10,000 | 19,999 | 19,999 |
| `redisson-rlock` | 67.8-68.0% | 67.6-68.0% | 10,000 | 10,000 | 0 | 0 |
| `optimistic` | 77.0% | **68.0-68.6%** | 5,546-5,552 | **8,784-8,786** | 88,502-88,512 | 78,792-78,840 |

- 행 락 두 방식은 풀 9 에서 실패율이 2회 평균으로 0.5-0.9%p 높았다. 같은 행 하나를 두고 줄을 서므로
  커넥션 수가 처리량을 거의 바꾸지 못한다.
- `redisson-rlock` 은 커넥션을 동시에 1개만 써서 풀 크기와 무관하다.
- `optimistic` 만 크게 달라졌다. 풀이 작아져 같은 순간 경합하는 요청이 줄자 실패율이 2회 평균으로 8.7%p 낮아지고
  발급이 3,200장 넘게 늘었다. [6.2](#62-인메모리라도-재시도-방식은-무너졌다) 의 해석을 직접 확인한 결과다.
- 풀 9 에서는 `optimistic`(68.0-68.6%)과 `redisson-rlock`(67.6-68.0%)의 범위가 맞닿는다.
  나머지 순위는 같다.

## 6. 결과 분석

`lua` 가 유일하게 **12초 안에 완판하고 오류도 0** 이었다.
원인은 DB 에 도달한 요청 수다.

20,000명이 10,000장을 두고 몰리면 요청의 절반이 거절이다. DB 판정은
**"품절입니다"라고 답하려고도 DB 에 가야 한다.** 재고가 남았는지 DB 에
물어봐야 알기 때문이다. 인메모리 판정은 Redis 가 거절을 쳐내므로 DB 에는
발급분만 도달한다.

| 방식 | INSERT | 롤백 | UPDATE | 행 락 대기 |
|---|---:|---:|---:|---:|
| `redis-lua` | **10,000** | **0** | **0** | **0** |
| `redis-watch` | 1,475-1,526 | 0 | 0 | 0 |
| `redisson-rlock` | 10,000 | 10,000 | 10,000 | **0** |
| `pessimistic-lock` | 10,000 | 10,000 | 10,000 | 19,999 |
| `atomic-update` | 10,000 | 10,000 | 20,000 | 19,999 |
| `optimistic` | **88,506-88,525** | **82,960-82,973** | 88,506-88,525 | **88,502-88,512** |

`lua` 는 INSERT 가 정확히 발급 수와 같고 롤백·락 대기가 모두 0 이다.
품절 1만 건이 DB 에 닿지 않았다는 뜻이다.

`Com_update` 는 방식마다 세는 단위가 다르다 — `atomic` 의 20,000 은 조건부
UPDATE 가 매 요청 실행된 것이고, `optimistic` 의 88,506 은 재시도마다 실행된
것이다. `redisson` 의 락 대기 0 은 분산락이 앞에서 직렬화해 DB 가 경합을
겪지 않은 결과다.

### 6.1 락 방식을 바꿔도 같은 그룹에 머문다

`pessimistic` 실패율 59.9-60.4% / `atomic` 57.0-57.6% — 2회 평균으로 2.8%p 차이다.
`SELECT ... FOR UPDATE` 로 걸든 조건부 `UPDATE` 한 문장으로 처리하든
**같은 행을 두고 줄을 선다는 구조**는 그대로다. 행 락 대기도 둘 다 19,999 로 같다.

두 방식 모두 풀 대기가 184 로 포화됐다. 워커 스레드 200 개 중 커넥션 16 개를
잡은 것을 뺀 나머지가 전부 대기했다는 뜻이다. 그동안 CPU 는 3/4 이 놀았다([6.4](#64-부하-구간-cpu)).

### 6.2 인메모리라도 재시도 방식은 무너졌다

**재고를 다 팔지 못한 방식은 재시도 계열 둘뿐이다.**

| 방식 | 판정 위치 | DB 발급 | 미판매 |
|---|---|---:|---:|
| `redis-watch` | 인메모리 | 1,475-1,526 | 8,474-8,525장 |
| `optimistic` | DB | 5,546-5,552 | 4,448-4,454장 |

충돌하면 다시 시도하는 전략인데, 2만 명이 같은 재고를 두고 동시에 달려들면
**5회 재시도 안에 이기지 못하는 요청이 대량으로 생긴다.** 서버가 포기하면
사용자는 빈손으로 끝나고, 그만큼 재고가 남는다.

`redis-watch` 가 더 많이 남긴 것은 경합 지점의 동시성이 높기 때문이다.

```
optimistic   커넥션 풀 16 이 스로틀 → 같은 순간 충돌하는 요청 최대 16개
redis-watch  스레드 200개가 그대로 Redis 로 → 최대 200개
```

**DB 의 병목이 낙관적 락의 경합을 줄여준 셈이다.** 풀을 9 로 줄이자 `optimistic` 의
발급이 8,784-8,786 으로 늘었다([5.1](#51-커넥션-풀-9)). 재시도 전략은 경합
동시성을 통제해야 성립한다.

### 6.3 Redis 를 써도 락만 옮기면 소용없다

`redisson-rlock` 은 Redis 를 쓰고도 실패율 67.8-68.0% 로 행 락 방식들보다 나쁘다.
`metrics` 의 `active = 1` 이 원인이다 — 분산락이 전 요청을 직렬화해
**DB 커넥션을 동시에 1개만 썼다.** 행 락 대기가 0인 것은 경합을 Redis 로
옮긴 결과지만, 그 대가로 병렬성이 사라졌다.

Redis 를 쓰는 것 자체는 도움이 되지 않았다. **무엇을 옮겼느냐가 갈랐다.**

### 6.4 부하 구간 CPU

k6 가 부하를 건 구간의 앱 서버 vmstat(1초 간격, 풀 16)이다. 앱·MySQL·Redis 가 쓴 CPU 의 합계다.

| 방식 | us | 유휴 평균 | 유휴 최저 |
|---|---:|---:|---:|
| `redis-lua` | 55.3-58.8% | 21.2-25.3% | 4-6% |
| `redis-watch` | 63.8-65.5% | 2.6-5.3% | 1-2% |
| `atomic-update` | 10.8-12.0% | 73.2-74.3% | 31-36% |
| `pessimistic-lock` | 10.3-10.6% | 74.9% | 34-44% |
| `redisson-rlock` | 10.8-11.3% | 72.8-73.4% | 29-52% |
| `optimistic` | 43.6-43.8% | 32.8-33.1% | 8% |

- 60초를 넘긴 행 락·분산락 방식은 CPU 의 3/4 이 놀았다. 느린 원인은 CPU 가 아니라
  같은 행(또는 같은 락)을 두고 기다리는 시간이다.
- `lua` 는 12초 동안 유휴 평균 21-25% 로 CPU 를 대부분 썼다. 행 락 대기는 0 이다.
- `redis-watch` 는 유휴 최저 1-2% 로 CPU 가 찼다. 실패는 전부 5xx 다.

## 7. 최종 선택

**재고 판정을 Redis 에서 원자적으로 처리하는 `redis-lua` 를 채택한다.**

Redis 사용 여부가 아니라 **무엇을 Redis 로 옮겼는가**가 갈랐다.

```
판정을 옮기고 원자적으로 처리   lua      12.0초 안에 완판 · 오류 0
판정을 옮겼으나 재시도에 맡김   watch    1,475-1,526장만 판매 · 실패 92.4-92.6%
락만 옮김                      redisson 60초 초과 · 실패 67.8-68.0%
```

`lua` 는 요청당 Redis 명령이 1회(`EVALSHA`)라 **충돌이라는 개념 자체가 없다.**
확인과 확정 사이에 틈이 없어 재시도할 일이 생기지 않는다.

## 8. 한계

- 요청 타임아웃 60초에 걸린 방식은 실제 소요 시간을 알 수 없다(60초 이상).
  실패율과 DB 발급 수는 잘리지 않은 값이다.
- 앱·MySQL·Redis 가 한 서버에서 CPU 를 나눠 쓴다. 부하 구간 CPU 는 셋의 합계다.
- 5xx 의 원인(재시도 소진, 커넥션 대기 상한 10초, Redis 명령 타임아웃 3초)은 나누지 않았다.
  앱 로그를 수집하지 않았다.
- `coupon_issue` 가 빈 상태에서 시작한다. 이력이 쌓이면 INSERT 비용이 늘어
  절대 수치는 달라진다.
- `lua` 도 DB 쓰기가 요청 경로에 남아 풀 대기가 184 까지 갔다. 다만 12초 안에
  끝나 지속되지 않았다. 완전히 풀려면 쓰기 비동기화가 다음 단계다.
  [backend](https://github.com/MO-COU/backend)의 최종 구조는 Redis Stream 비동기 적재다.
