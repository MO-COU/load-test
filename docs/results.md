## redis-lua

Lua 스크립트로 중복 확인·재고 확인·차감·회원 등록을 Redis 안에서 원자적으로 처리하고,
통과한 요청만 DB 에 이력을 남긴다.

```
k6        12.0s · 20,000 요청 · p95 11.2~11.4s · 실패 0%
          발급 10,000 · 품절 10,000 · 완판 11.1s
dbstat    insert +10,000 · rollback 0 · update 0 · row_lock_waits 0
redis     요청당 EVALSHA 1회 (코드 기준)
metrics   active 16/16 · pending 184 · threads 200/200
verify    DB 발급 10,000 (완판) · oversell PASS · duplicate PASS · 재고누수 PASS
CPU       us 55~59% · 유휴 21~25% (최저 4~6%) · accept 큐 최대 7,156~13,315
```

품절 1만 건이 Redis 앞에서 끝나 DB 에는 발급 1만 건만 도달했다.
`Com_insert` 가 정확히 발급 수와 일치하고 롤백·락 대기가 0이다.

풀 대기 184 는 DB 방식과 같지만 지속 시간이 다르다. 12초 안에 끝나고 비워진다.
그 12초 동안 CPU 를 대부분 썼다.

## redis-watch

`WATCH`/`MULTI`/`EXEC` 로 낙관적 예약을 시도하고, 충돌하면 최대 5회까지 시도한다.

```
k6        18.6~18.7s · 20,000 요청 · p95 17.7s · 실패 92.4~92.6% (전부 5xx, 중앙값 11.4~11.5s)
          발급 1,475~1,526 · 재고 8,474~8,525장 미판매
dbstat    insert +1,475~1,526 · rollback 0 · update 0 · row_lock_waits 0
metrics   active 2~4 · pending 0 · threads 200/200
verify    oversell PASS · duplicate PASS · 재고누수 PASS
CPU       us 64~66% · 유휴 3~5% (최저 1~2%) · accept 큐 최대 13,213~13,236
```

**가장 빨리 끝나지만 가장 적게 팔았다.** 초과 발급은 없으니 정합성은 지켰고,
받을 수 있었던 8,474~8,525명이 못 받았다.

스레드 200개가 그대로 Redis 로 몰려 WATCH 충돌이 폭증한다. 확인(`GET`)과
확정(`EXEC`) 사이에 남이 끼어들어 5번의 시도가 대부분 소진된다. 실패는 전부 5xx 다.

## pessimistic-lock

`SELECT ... FOR UPDATE` 로 쿠폰 행에 배타 락을 걸고 재고 확인부터 증가까지 직렬화한다.

```
k6        60s+ ⏱ · 20,000 요청 · p95 59.9s ⏱ · 실패 59.9~60.4% (전부 타임아웃)
          k6 발급 7,920~8,028
dbstat    insert +10,000 · rollback +10,000 · update +10,000 · row_lock_waits +19,999
metrics   active 16/16 · pending 184 · threads 200/200
verify    DB 발급 10,000 (완판) · oversell PASS · counter_ok PASS · duplicate PASS
CPU       us 10~11% · 유휴 75% (최저 34~44%) · accept 큐 최대 8,450~8,517
```

CPU 는 놀고 있는데 느리다. 락 대기와 커넥션 대기가 병목이라는 뜻이다.
`atomic` 과 락 대기가 19,999 로 같다 — 락을 거는 방법을 바꿔도 줄 서는 구조는 그대로다.

## redisson-rlock

Redis 분산락(`RLock`)을 잡고 그 안에서 DB 트랜잭션을 실행한다.

```
k6        60s+ ⏱ · 20,000 요청 · p95 59.9s ⏱ · 실패 67.8~68.0% (전부 타임아웃)
          k6 발급 6,406~6,434
dbstat    insert +10,000 · rollback +10,000 · update +10,000 · row_lock_waits 0
metrics   active 1 · pending 0 · threads 200/200
verify    DB 발급 10,000 (완판) · oversell PASS · counter_ok PASS · duplicate PASS
CPU       us 11% · 유휴 73% (최저 29~52%) · accept 큐 최대 7,951~11,497
```

**Redis 를 쓰고도 행 락 방식들보다 실패율이 높다.** 원인은 `active = 1` —
분산락이 전 요청을 직렬화해 DB 커넥션을 동시에 1개만 쓴다.
행 락 대기 0 은 경합을 Redis 로 옮긴 결과지만 그 대가로 병렬성이 사라졌다.

## optimistic

`@Version` 으로 충돌을 감지하고 최대 5회까지 시도한다.

```
k6        60s+ ⏱ · 20,000 요청 · p95 59.9s ⏱ · 실패 77.0%
          (5xx 11,895~11,937, 중앙값 32.5~32.7s · 타임아웃 3,461~3,513)
          k6 발급 4,592~4,602 · 재고 4,448~4,454장 미판매
dbstat    insert +88,506~88,525 · rollback +82,960~82,973 · update +88,506~88,525 · row_lock_waits +88,502~88,512
metrics   active 16/16 · pending 181 · threads 200/200
verify    DB 발급 5,546~5,552 · oversell PASS · counter_ok PASS · duplicate PASS
CPU       us 44% · 유휴 33% (최저 8%) · accept 큐 최대 10,408~13,703
```

**DB 부하가 압도적으로 많다** — INSERT·락 대기 모두 8.9만으로 다른 방식의 4-9배다.
충돌한 요청이 되돌아와 다시 경합하면서 부하만 키웠다. 행 락 방식과 달리 CPU 도 많이 썼다.

재고도 다 팔지 못했다. 5번의 시도 안에 이기지 못한 요청이 그만큼 많았다는 뜻이다.

DB 판정 4방식을 풀 9 로도 2회씩 쟀다. 같은 서버에서 방식마다 16 → 9 → 16 → 9 순으로 번갈아 돌렸다.

## 해석할 때 주의

**`60s+ ⏱` 는 잘린 값이다.** k6 요청 타임아웃 60초에 걸린 것으로 실제로는 그 이상
걸렸다. 그래서 방식 간 비교에는 소요 시간 대신 **실패율과 DB 발급 수**를 쓴다.

**DB 발급은 서버가 배수를 끝낸 뒤 세었다.** k6 는 60초에서 포기하지만 서버는 밀린
요청을 계속 처리한다. 바로 세면 처리 중인 건이 빠져 실제보다 적게 나온다.

**행 락·분산락 방식의 실패는 커넥션 대기가 아니라 그 앞에서 났다.** 커넥션 대기 상한 10초에
걸린 5xx 가 0 이다. 워커 스레드 200개가 찬 동안 나머지 요청은 스레드 앞에서 기다리다 60초에 잘렸다.
이 방식들은 60초 안에 `409` 품절 응답을 하나도 받지 못했다. 60초 동안 처리된 요청이 재고 1만 장에 못 미쳐, 품절을 판정할 차례가 오기 전에 잘렸다.

**`Com_update` 는 방식마다 세는 단위가 다르다.** MySQL 은 실행된 UPDATE 문을
세지 변경된 행을 세지 않는다.

| 방식 | `Com_update` 가 세는 것 |
|---|---|
| `pessimistic`·`redisson` | 발급 성공 시 dirty checking 으로 1회 → **발급 수** |
| `atomic-update` | 조건부 UPDATE 가 매 요청 실행 → **전체 요청 수** |
| `optimistic` | 재시도마다 실행 → **시도 수** |

**`counter_ok` 가 Redis 방식에서 N/A 인 이유.** 재고 판정을 Redis 가 하므로
`coupon.issued_count` 를 갱신하지 않는다. 모든 요청이 같은 행을 UPDATE 하면
직렬화되어 인메모리 판정의 이점이 사라지기 때문이다.

**`watch` 의 실패는 Redis 처리량이 아니라 WATCH 충돌이다.** 같은 서버에서 `lua` 가
`watch` 보다 초당 더 많은 요청을 오류 없이 처리했다. 다만 `watch` 는 부하 구간 CPU 유휴가
평균 3-5%, 최저 1-2% 였고, CPU 경합이 충돌 구간을 늘렸는지는 이 측정으로 나누지 않았다.

**accept 큐 최대 깊이는 6,715-14,155 였다.** Tomcat 기본값 100 이었다면 연결이
대량 폐기됐을 것이다. 최대 깊이가 설정한 32768 의 절반에 못 미쳐 큐는 넘치지 않았다.

**CPU 는 부하 구간만 잘라 본다.** `after.sh` 가 출력하는 평균은 부하 전후의 유휴 구간을 포함해
빠르게 끝나는 방식일수록 유휴가 높게 보인다. 이 문서의 CPU 는 k6 종료 시각에서 실행 시간만큼 거슬러 올라간 구간의 vmstat 값이다.
