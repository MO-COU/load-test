# 동기 적재 실험 — 분석 노트

Stage 0~4 측정 결과(각 `sync/stage-N.md`)를 보면서 나온 질문과 결론을
기록한다. 수치 표는 각 stage 문서에 있고, 여긴 **왜 그런 결과가 나왔는지**
설명이 목적이다.

## 1. Tomcat 스레드·HikariCP 풀은 몇 개가 적당한가

**원칙**: 스레드 수는 다운스트림 자원(DB 커넥션 풀)이 감당할 수 있는
만큼만 의미가 있다. 블로킹 I/O 워크로드(요청 처리 시간의 대부분이 DB
응답 대기)에서 스레드가 커넥션 풀보다 훨씬 많으면, 초과분은 그냥
**커넥션 자리를 기다리며 노는 스레드**가 된다.

우리 설정(스레드 200 / 풀 50 = 4배)이 정확히 이 상황을 보여줬다.
VU=200에서 스레드 200개가 다 찼는데, 그중 144~149개는 `hikari_pending`
— 실제로 일 안 하고 커넥션 빈 자리만 기다리는 상태였다. 이 150개는
처리량에 0 기여하면서 메모리(스레드당 스택)와 컨텍스트 스위칭 비용만
썼다.

### 트레이드오프

| 스레드를 | 얻는 것 | 잃는 것 |
|---|---|---|
| 늘리면 | 순간적으로 몰리는 요청을 더 많이 "접수"는 해줌(큐잉 여유) | 메모리·컨텍스트 스위칭 낭비. 풀이 못 받쳐주면 대기 줄만 길어져 p95만 나빠짐 |
| 줄이면 | 노는 스레드가 줄어듦, 초과 요청은 빨리 거절(fail-fast)돼서 시스템이 덜 흔들림 | 순간 버스트 흡수 여유가 줄어 짧은 스파이크에도 거절이 빨리 남 |

### 실무 기준

블로킹 I/O 워크로드에서 흔한 경험칙: **스레드 수 ≈ 커넥션 풀 크기의
1.5~2배**. 우리처럼 4배로 벌리진 않는다. 지금 설정 기준이면 풀=50 그대로
두고 스레드는 75~100 정도가 적당해 보인다 — 처리량 한계(어차피 DB 풀
50이 병목)는 그대로 유지하면서, 쓸데없이 노는 스레드를 줄여 메모리
여유를 확보하고 fail-fast를 더 낮은 VU에서 빨리 드러나게 한다.

## 2. 왜 풀·스레드를 무한정 늘려도 성능이 안 오르는가

결국 병목은 **MySQL 서버 자체가 실제로 동시에 처리할 수 있는 양**이다.
풀을 키우는 건 "문을 더 여는 것"이지 "일꾼을 늘리는 것"이 아니다.
MySQL 쪽에서 막히는 지점 3가지:

1. **CPU 코어 수** — 코어 개수만큼만 진짜 병렬로 일한다. 커넥션을 더
   열어도 코어 이상으로 동시에 실행되진 않고 컨텍스트 스위칭만 늘어난다.
2. **디스크 fsync 상한** — `innodb_flush_log_at_trx_commit=1`이라 커밋마다
   fsync한다. 초당 가능한 fsync 횟수는 디스크 하드웨어가 정한 물리적
   상한이라 커넥션을 아무리 열어도 못 넘는다.
3. **InnoDB 내부 락/뮤텍스 경합** — 버퍼 풀, redo log, 인덱스 페이지 같은
   공유 자료구조를 동시에 만지는 커넥션이 많을수록 서로 기다리는 시간이
   늘어난다(`Innodb_row_lock_waits` 증가로 관측).

**일정 지점을 넘으면 처리량이 오히려 떨어질 수도 있다.** 동시에 일하는
주체가 너무 많아지면 서로 부딪히고 기다리는 시간이 일하는 시간보다
커지는 현상(줄서기 이론의 "thrashing")이다.

## 3. 적정 크기를 실측하는 방법 (아직 안 함 — 방법만 정리)

지금까지 한 "VU 스윕"과는 축이 다르다. 그건 **부하(VU)를 고정된
풀·스레드에 던져서 어디서 터지는지** 봤고, 풀·스레드의 적정값을 찾으려면
**풀·스레드 크기 자체를 바꿔가며 처리량이 어디서 꺾이는지** 봐야 한다.

1. **커넥션 풀 스윕**: VU를 충분히 높게 고정(예: 200), `DB_POOL_SIZE`를
   10→20→30→50→75→100→150로 바꿔가며 앱을 재시작하고 매번 처리량을
   기록. 이론적 하한선은 Little's Law로 먼저 가늠: `필요 풀 크기 ≈
   목표 처리량(req/s) × 평균 커넥션 점유시간(s)`.
2. **Tomcat 스레드 스윕**: 1번에서 찾은 최적 풀 크기로 고정하고,
   `TOMCAT_MAX_THREADS`를 풀 크기의 1x/1.5x/2x/4x(현재값)로 바꿔가며
   비교. 처리량은 어느 시점부터 거의 안 바뀌어야 정상(병목이 이미 풀로
   넘어갔으므로) — 그 지점을 지나서 스레드를 올리는 건 메모리만 쓰는 것.

env var(`DB_POOL_SIZE`, `TOMCAT_MAX_THREADS`, `TOMCAT_ACCEPT_COUNT`)는
`application.yaml`에 이미 다 빠져 있어서 코드 수정 없이 재시작만으로
가능하다. 다만 이 스윕은 설정 바꿀 때마다 **앱을 재시작**해야 해서
VU 스윕보다 손이 훨씬 많이 간다 — 필요할 때 자동화 스크립트로 만들기로
하고 보류.

## 4. 로컬 측정 환경의 특성

- **호스트 CPU**: 12코어. Docker Desktop에도 12 CPU 전부 할당돼 있고
  `mysql-large` 컨테이너 자체엔 별도 CPU 제한 없음(`NanoCpus: 0`).
  즉 MySQL이 쓸 수 있는 CPU 상한 = 이 PC의 12코어 그대로지만, 앱·k6·
  Docker Desktop 자체와 나눠 쓰는 것이라 순간적으로는 이보다 적게 쓸 수
  있다.
- **`innodb_os_log_fsyncs`는 PC마다 다르다**: 물리 디스크 종류(NVMe/
  SATA/HDD)뿐 아니라, **Docker Desktop for Windows가 WSL2 위에 가상
  디스크(VHDX)를 만들고 그 안의 Docker volume에 MySQL이 쓰는 구조**라
  한 겹 더 가상화가 끼어 있다. 같은 PC라도 Docker Desktop 설정에 따라
  달라질 수 있는, **이 실험 환경에 고유한 값**이라 절대 수치를 다른
  환경과 비교하면 안 된다.

## 5. fsync 물리적 상한에 실제로 닿은 구간은 어디인가

fsync **횟수**가 아니라 **초당 처리율**(`fsync_delta ÷ 경과시간`)로
봐야 한다. 상한에 닿았다면 VU를 올려도 이 값이 평평해진다.

| Stage | VU 10 | VU 50 | VU 100 | VU 200 | VU 300 | VU 400 | VU 500 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Stage 1 (30만) | 891/s | 343/s | 341/s | 409/s | 347/s | 416/s | 396/s |
| **Stage 4 (300만)** | 178/s | 165/s | 155/s | 166/s | 169/s | 162/s | 162/s |

**Stage 4에서 가장 뚜렷한 상한 신호가 보인다.** VU를 10에서 500까지
50배 올렸는데도 fsync 처리율이 155~178/s 사이에서 거의 고정 — 이
환경의 물리적 fsync 상한에 도달한 것으로 해석한다. Stage 1~3은 343~900
/s 사이로 더 높고 들쭉날쭉한데, 이건 상한이라기보다 InnoDB의 **group
commit**(여러 트랜잭션 커밋을 fsync 한 번에 묶는 최적화)이 아직 여유
있게 작동한 결과로 본다.

## 6. Stage 4가 터진 원인 — 인덱스 부재? CPU? 버퍼 풀?

### 인덱스는 있다

`coupon_issue`엔 인덱스 3개가 다 있다(`PRIMARY`,
`uk_coupon_issue_coupon_member(coupon_id, member_id)`,
`idx_coupon_issue_member_issued_at(member_id, issued_at)`). **인덱스가
없어서가 아니라, 있는 인덱스의 크기가 캐시보다 커져서** 생긴 문제다.

### 버퍼 풀 = MySQL(InnoDB) 프로세스 자신의 메모리

"서버(OS)의 범용 버퍼"가 아니라 **MySQL이 기동할 때 확보하는 전용 RAM
캐시**다(`innodb_buffer_pool_size`). OS 파일 캐시도 별도로 있지만,
지금 병목은 그보다 상위 레이어인 InnoDB 자체 캐시다.

### 실측 근거

| 항목 | 크기 |
|---|---:|
| `coupon_issue` 데이터 | 177.7 MB |
| 인덱스 3개 합 | 193.0 MB |
| **합계** | **370.7 MB** |
| `innodb_buffer_pool_size` | **128 MB**(기본값, 미조정) |

테이블+인덱스가 캐시의 거의 3배라 65%가 디스크에 있다. Stage 0~3(≤150만
건)까진 테이블이 128MB보다 작아 다 캐시에 들어갔는데, Stage 4(300만
건)에서 처음 이 경계를 넘었다 — 시점이 정확히 일치한다.

### 그런데 CPU를 완전히 배제할 순 없다

- **수학적으로 CPU만으론 설명이 약함**: B+Tree 탐색 비용은 `O(log n)`.
  1만→300만 건이면 트리 깊이 차이는 8단계 정도(log₂(3,000,000) -
  log₂(10,000) ≈ 8)뿐이라, 이걸로 2.5배 지연 증가를 설명하긴 어렵다 —
  디스크 I/O 대기가 끼어들어야 설명이 된다.
- **하지만 물리 읽기(`innodb_buf_reads`) 수치는 깨끗하지 않다**: VU=10
  기준 Stage 1=0, Stage 2=822, Stage 3=**1,031**, Stage 4=927 —
  Stage 4가 Stage 3보다 오히려 적다. 버퍼 풀이 원인이면 Stage 4에서
  확 튀어야 하는데 그렇지 않다.
- **놓친 변수**: Stage 4 시딩(300만 건, 52초)을 하고 바로 VU 스윕을
  돌려서, dirty page flush가 덜 끝난 상태가 섞였을 가능성이 있다.
  CPU 사용률도 한 번도 직접 측정한 적이 없다(`docker stats` 안 씀).

**결론**: 버퍼 풀(디스크 I/O) 쪽이 CPU보다 유력하지만 확정은 아니다.
검증하려면 (1) `innodb_buffer_pool_size`를 512MB~1GB로 올려 Stage 4
재측정(버퍼 풀 원인이면 VU=10 기준선이 8ms대로 복귀해야 함), (2)
테스트 중 `docker stats`로 CPU 실측, (3) 시딩 후 정착 시간을 두고
재측정 — 세 가지가 필요. **사용자 요청으로 보류 중.**

## 7. 비동기(배치) 적재로 바꾸면 예상되는 변화

### 개선될 것

1. **VU=200 근처 스레드 포화가 뒤로 밀림** — 요청 스레드가 DB 응답을
   기다리며 블로킹되지 않고 큐에 넣고 바로 응답하므로, 스레드 하나가
   DB 작업을 붙잡는 시간이 ms 단위에서 마이크로초 단위로 줄어든다.
2. **VU=500의 TCP 연결 거부 실패가 줄거나 훨씬 높은 VU에서만 나타남**
   — 스레드가 안 막히니 Tomcat accept 큐가 순간적으로 넘칠 확률이
   낮아진다.
3. **fsync 부담 감소** — N건을 한 트랜잭션에 묶어 커밋하면 fsync 1번으로
   N건이 처리된다. Stage 4에서 본 "fsync 처리율이 VU 무관하게 고정"되는
   병목의 실질 상한이 올라갈 것으로 예상.

### 여전히 안 풀릴 것

1. **Stage 4의 동시성과 무관한 기본 지연 증가** — 버퍼 풀 초과가 원인이면
   동기든 비동기든 같은 인덱스 페이지를 읽고 쓰는 건 똑같아서 안 없어짐.
2. **MySQL 서버 자체의 물리적 한계**(CPU 12코어, 디스크 I/O 대역폭) —
   비동기는 "얼마나 오래 기다리게 하느냐"를 바꾸는 거지 "일꾼 수"를
   늘리는 게 아니다.
3. **Row lock 경합**은 배치로 묶어도 근본적으로 남고, 배치 크기를
   잘못 잡으면 한 트랜잭션이 여러 행을 더 오래 잠가 오히려 나빠질 수도
   있다.

### 새로 생기는 문제

1. **정합성 유실 창** — "응답 옴 = 큐에 들어감"으로 의미가 바뀐다.
   응답 직후 DB를 조회하면 아직 없을 수 있는 시간차가 생긴다.
2. **크래시 시 데이터 유실** — 가장 단순한 구현(인메모리 큐)이면 큐에
   쌓인 채로 앱이 죽으면 그 요청들은 통째로 사라진다. 동기보다 오히려
   나빠질 수 있는 지점 — Redis Stream 같은 영속 큐를 쓰기로 한 이유.
3. **백프레셔** — 들어오는 속도가 비우는 속도보다 계속 빠르면 결국
   큐가 무한정 쌓인다. 지금은 "연결 거부"로 명확히 터졌는데, 비동기는
   대신 메모리 부족으로 죽거나 응답 지연이 한없이 느는 형태로 나타날
   수 있다 — 새로 측정해야 할 실패 모드.

## 8. 인메모리 큐 vs Redis — 메모리 기반이면 둘 다 똑같이 죽는 거 아닌가

아니다, 결정적 차이가 있다.

| | 앱의 인메모리 큐(순진한 구현) | Redis |
|---|---|---|
| 메모리 위치 | Spring Boot 앱의 JVM 힙 — Tomcat·비즈니스 로직과 같은 메모리 | 별도 프로세스, 독립된 메모리 공간 |
| 가득 찼을 때 | 정해진 게 없음 → 계속 커지다 `OutOfMemoryError` | `maxmemory` 설정 + eviction 정책으로 동작을 직접 정할 수 있음 |
| 죽으면 | **앱 전체가 죽음**(Tomcat도 다른 API도 같이) | Redis만 영향받음, 앱은 재시도/서킷브레이커로 대응 가능 |

Redis를 쓴다고 저절로 안전해지는 게 아니라, **가득 찼을 때 뭘 할지
명시적으로 정해야 한다.** `maxmemory-policy noeviction`(꽉 차면 새
쓰기 거부) + Stream의 `MAXLEN`(최대 길이 제한)으로 "이 이상 쌓이면
새 요청을 거부한다"는 정책을 직접 정해야, 지금 동기 방식에서 본
"TCP 연결 거부"에 대응하는 **깨끗한 실패 모드**를 비동기에서도 가져갈
수 있다. `allkeys-lru` 같은 정책은 큐 용도로는 위험하다 — 아직 DB에
안 들어간 대기 중인 데이터가 지워질 수 있어서, 정합성을 지키려고
Redis Stream을 쓰기로 한 목적과 정면으로 배치된다.
