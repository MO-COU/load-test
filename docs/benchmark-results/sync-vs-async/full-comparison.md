# 동기 vs 비동기 전체 데이터 비교표

Stage 0~4, INSERT만/INSERT+UPDATE, VU 10~500 전 구간에서 측정한
**응답(클라이언트가 보는) 지표**를 동기·비동기(nobatch)·비동기
(batch100) 세 조건 나란히 모은 표다. 각 조건·각 stage의 원본 데이터와
상세 해석(왜 이런 수치가 나왔는지)은 아래 문서에 있다 — 이 표는 그
결과들을 한 화면에서 비교하기 위한 요약이다.

- 동기: [`sync/stage-0.md`](sync/stage-0.md) ~ [`stage-4.md`](sync/stage-4.md)
- 비동기: [`async/stage-0.md`](async/stage-0.md), [`async/stage-1-to-4.md`](async/stage-1-to-4.md)
- 왜 이런 차이가 나는지: [`analysis-notes.md`](analysis-notes.md)

## 표 읽는 법

- **Avg/p95**: 클라이언트(k6)가 측정한 요청-응답 시간. 동기는 "DB 커밋까지
  끝난 시간", 비동기는 **"큐에 넣고 202 받은 시간"**이라 서로 재는 게
  다르다 — 비동기가 훨씬 빠른 건 당연하고, 이 표만 보고 "비동기가
  10배 빠르다"고 결론 내리면 안 된다. 비동기가 실제로 DB에 다 반영되는
  데 걸리는 시간은 **drain**(비동기 두 조건에만 있는 열)을 봐야 한다.
- **실패율**: 셋 다 같은 의미(HTTP 요청 실패, 대부분 TCP 연결 거부) —
  이 열은 세 조건을 직접 비교해도 된다.
- **drain**: k6가 끝난 뒤 큐가 완전히 빌 때까지 걸린 시간(초). `60s*`는
  `DRAIN_TIMEOUT_SEC=60` 컷오프에 걸려 못 비운 것 — "60초"가 아니라
  "60초보다 김"으로 읽는다.
- 굵게 표시한 값은 각 stage·워크로드에서 특히 눈에 띄는(포화·급증·이상치)
  지점이다.
- 동기 Stage 0에는 VU 30·333 지점도 있지만(`sync/stage-0.md` 참고), 세
  조건이 공통으로 가진 VU(10·50·100·200·300·400·500)만 이 표에 실었다.

## 한눈에 보는 결론

- **응답 지연**: 비동기(nobatch·batch100 둘 다)는 전 Stage·전 VU에서
  동기보다 압도적으로 빠르다(수 ms대 vs 수십~수백 ms대) — 다만 이건
  "DB 커밋까지 기다리지 않고 큐에 넣자마자 응답한다"는 계약 차이일
  뿐, 배치 유무와는 무관하다(위 "표 읽는 법" 참고).
- **실패율**: 동기는 Stage와 무관하게 VU=300~500대에서 실패율이
  튀는 게 일정한 패턴이다(Stage 0 INSERT+UPDATE 24.11%가 최고치).
  비동기는 대부분 한 자릿수 %이거나 0%다.
- **동기의 Stage 4 전용 병목**(VU=10 기준선이 8ms대에서 20ms대로
  뜀)은 비동기 두 조건 모두의 응답 지연에서는 안 보인다 — 비동기의
  응답 지연이 애초에 DB를 안 보기 때문.
- **배치 유무의 진짜 차이는 이 표의 avg/p95가 아니라 drain 열에
  있다.** batch100은 전 Stage에서 drain이 6~7초(INSERT만)/12~14초
  (INSERT+UPDATE)로 고정인데, nobatch는 Stage 2(90만)부터 VU=10에서도
  60초를 못 채운다. Stage 0~1에서는 nobatch도 49~60초 안에 어떻게든
  비웠지만, Stage 2 이후로는 컨슈머가 사실상 부하를 따라잡지 못한다.
- 굵게 표시된 이상치(Stage 0 VU=400 INSERT만 실패율 7.55%, Stage 2
  batch100 VU=400 INSERT+UPDATE 실패율 10.33%, Stage 4 batch100
  VU=500 INSERT만 실패율 16.22%, Stage 4 nobatch VU=500 INSERT+UPDATE
  p95 71.22ms)는 전후 값과 비교해 단조롭지 않은 단일 지점이라 로컬
  Windows 환경의 TCP/포트 노이즈로 본다 — 재현성 검증은 안 됐다.
