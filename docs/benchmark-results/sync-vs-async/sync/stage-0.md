# Stage 0 측정 결과 (동기 적재)

배경 데이터: `coupon_issue` 정확히 10,000건(`seed-stage0-trim.sql`).
요청 총량은 VU가 달라져도 ~10,000건으로 고정하고 VU(동시성)만 올렸다.
원본 시계열과 자동 집계 요약은 [`../raw/stage0.tsv`](../raw/stage0.tsv)에 있다.
측정 스크립트는 [`../../../sync-vs-async-loading-experiment.md`](../../../sync-vs-async-loading-experiment.md)의
"Stage 0 실행 방법"을 그대로 따랐다(`load-test/large-db-insert.js`,
`load-test/large-db-insert-then-update.js`, `scripts/large-db/run-vu-sweep.sh`).

VU 지점은 10·30·50·100·200을 먼저 찍고, 300·333·400·500을 여러 차례에
걸쳐 추가했다. 그 과정에서 `run-vu-sweep.sh`의 요약 이어쓰기 로직에 버그가
있어(`grep`의 `\t`가 이 환경에서 탭으로 해석되지 않음) 한 번 요약이
유실됐으나, k6 로그 원본이 남아있어 전부 복구했다. 스크립트는 고쳤다.

`*` 해당 실행은 4~5초 만에 끝나 1초 간격 폴링이 부하 구간을 못 잡았다
(샘플링 공백). 이 줄들은 `hikari_pending`/`tomcat_busy` 값을 신뢰하지
말고, k6 로그에서 뽑은 Avg/p95/실패율만 신뢰한다.

`†` INSERT만의 실패율이 VU=400(7.55%)이 VU=500(2.78%)보다 높게 나와
역전됐고, 300(0.51%)·333(1.51%)과 비교해도 매끈하지 않다 — 로컬
Windows 환경에서 직전 실행이 남긴 TIME_WAIT 소켓 상태에 따라 "연결
거부"가 실행마다 다르게 터지는 노이즈로 본다. INSERT+UPDATE는
0%→0.02%→1.52%→1.69%→24.11%로 훨씬 단조에 가깝다 — INSERT만의 정확한
실패율보다는 "VU 200대에서 포화, 400~500대에서 실패 급증"이라는 큰
그림으로 해석한다.

`row_lock_waits`는 MySQL 시작 이후 누적되는 전역 카운터인데, 이 VU
지점들을 여러 차례에 걸쳐 순서 없이(10~200 → 500 → 400 → 333 → 300 순으로)
추가해서 표의 VU 오름차순과 실제 실행 순서가 어긋난다. 그래서 Stage 0는
"직전 줄과의 차이"로 새 lock wait 발생량을 해석할 수 없다 — 이 표에서는
뺐다. Stage 1~4는 각 스테이지를 한 번에 VU 오름차순으로 실행해 이 문제가
없으니, row lock 관련 해석은 그쪽 문서를 참고한다.

## 분석

### 1. VU=200 — 포화의 첫 신호 (실패는 아직 없음)

Tomcat 워커 스레드(최대 200개)가 두 워크로드 모두에서 완전히 꽉 찼고,
`hikari_pending`(커넥션 풀 대기)이 144~149까지 치솟았다. 즉 200개 스레드 중
**절반 이상이 50개짜리 DB 커넥션 풀에서 빈 자리를 기다리는 상태**였다.
아직 요청은 전부 성공하지만 p95가 VU=10 대비 13~17배 느려졌다(INSERT만
11ms → 194ms, INSERT+UPDATE 12ms → 146ms).

### 2. VU=300부터 실패가 조금씩 시작, VU=500에서 확실히 터짐

INSERT+UPDATE 기준 VU=300부터 실패가 나타나기 시작하고(0.02%→1.52%→1.69%)
VU=500에서 24.11%로 급증한다. VU=500의 실패는 4xx/5xx 같은 애플리케이션
에러가 아니라 OS/Tomcat 레벨의 TCP 연결 거부였다.

```
dial tcp 127.0.0.1:8080: connectex: No connection could be made
because the target machine actively refused it.
```

요청이 컨트롤러 코드에 도달하기도 전에 끊겼다는 뜻이다. INSERT+UPDATE가
INSERT만보다 훨씬 심하게 터졌다(24.11% vs 2.78%) — 같은 iteration 안에서
DB 왕복을 2번(INSERT, UPDATE) 하기 때문에 스레드·커넥션을 그만큼 더 오래
붙잡는다.

### 3. 정합성 손실 — 실패한 요청은 그냥 사라진다

VU=500 INSERT+UPDATE 실행 후 실제 DB엔 10,000건 중 **7,589건만** 적재됐다
(`verify-benchmark.sql` 확인). 동기 방식엔 재시도·큐잉이 없어서, 거부된
요청은 클라이언트가 별도로 재시도하지 않는 한 그대로 유실된다.
