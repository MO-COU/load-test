# Stage 1~4 측정 결과 (비동기 배치 적재) + Stage 0~4 종합

Stage 0([`stage-0.md`](stage-0.md))와 같은 조건으로, 배경 데이터만
[`docs/large-db-experiment.md`](../../../large-db-experiment.md)의
Stage 1~4(30만~300만)로 늘려가며 nobatch(BATCH_SIZE=1)·batch100(기본값)
두 조건을 반복했다. 요청 총량은 각 단계에서 항상 ~10,000건(INSERT만)
/ ~10,000건(INSERT+UPDATE)으로 고정, VU만 10~500으로 올렸다.

원본: [`../raw/stage{1..4}-async-{nobatch,batch100}.tsv`](../raw/).
측정 스크립트: `scripts/large-db/run-vu-sweep-async.sh`.

## 측정 중 있었던 사고 — Stage 1 nobatch 재측정

Stage 1 nobatch를 처음 백그라운드로 실행할 때, 셸 도구 호출이 끝나며
스크립트가 죽은 줄 알았던 첫 시도가 실제로는 **고아 프로세스로 계속
살아남아 있었다.** 뒤이어 "깨끗하게" 다시 실행한 두 번째 시도와 두
프로세스가 **동시에 같은 앱·DB·큐를 두고 경합**했고, 그 결과 원본
tsv에 `# ===== Summary` 블록이 두 번 찍히는 등 오염된 데이터가
나왔다. 오염된 원본은 지우지 않고 `stage1-async-nobatch.tsv.CONTAMINATED.bak`
로 보관했고, Stage 1 nobatch만 재시딩 후 다시 측정해 아래 표는 전부
**정상적으로 완주한 단일 실행** 기준이다. 다른 7개 조합(Stage
1 batch100, Stage 2~4 nobatch/batch100)은 `# ===== Summary`가 한 번씩만
나와 오염되지 않았다.

이 사고 이후로는 백그라운드 실행에 항상 도구가 직접 추적하는 방식
(`run_in_background`)만 썼고, 셸의 `&`+`disown`으로 직접 백그라운드
처리하지 않았다 — Windows/Git Bash에서는 후자가 도구 호출 종료 후에도
고아 프로세스로 남을 수 있다는 걸 이번에 확인했다.

## 결과 표 — 응답(생산자) 측 지표

Stage 0와 마찬가지로 nobatch·batch100의 Avg/p95/처리량은 거의 겹친다
(응답은 큐잉만 확인하고 끝나므로 당연하다). 아래는 VU=10과 VU=500만
뽑은 요약이다 — 전 VU 구간 원본은 raw tsv 참고.

| Stage(배경 데이터) | 조건 | INSERT만 VU10 avg/p95 | INSERT만 VU500 avg/p95/실패율 | INSERT+UPDATE VU500 avg/p95/실패율 |
| --- | --- | --- | --- | --- |
| 1 (30만) | nobatch | 656µs / 1.64ms | 11.03ms / 29.14ms / 0.62% | 9.04ms / 23.8ms / 1.63% |
| 1 (30만) | batch100 | 448µs / 1.06ms | 11.57ms / 24.48ms / 1.21% | 10.82ms / 23.93ms / 1.38% |
| 2 (90만) | nobatch | 398µs / 1ms | 6.19ms / 16.97ms / 2.74% | 11.4ms / 27.72ms / 1.60% |
| 2 (90만) | batch100 | 535µs / 1.51ms | 10.4ms / 26.28ms / 1.58% | 12.82ms / 28.57ms / 0.57% |
| 3 (150만) | nobatch | 520µs / 1.5ms | 5.65ms / 14.51ms / 2.88% | 10.52ms / 29.37ms / 1.05% |
| 3 (150만) | batch100 | 513µs / 1.32ms | 8.32ms / 19.18ms / 2.38% | 9.72ms / 24.49ms / 2.29% |
| 4 (300만) | nobatch | 571µs / 1.51ms | 8.83ms / 23.02ms / 2.21% | **19.05ms / 71.22ms** / 0.88% |
| 4 (300만) | batch100 | 503µs / 1.29ms | 6.96ms / 11.6ms / **16.22%** | 11.75ms / 27.83ms / 1.82% |

**응답 지연 자체는 Stage가 올라가도(1만→300만) 거의 안 변한다** —
VU=10 기준 400~650µs대에서 계속 유지된다. 이건 Stage 0에서 이미
확인한 것과 같은 이유다: 응답은 "JVM 힙 큐에 넣었다"만 확인하고
끝나서 배경 데이터 크기·DB 상태를 전혀 안 본다.

두 지점만 눈에 띈다 — **(1)** Stage 4 nobatch INSERT+UPDATE VU=500에서
p95가 71.22ms로 다른 모든 지점(대부분 30ms 이하)보다 튀었다. **(2)**
Stage 4 batch100 INSERT만 VU=500에서 실패율이 16.22%로 유독 높다.
둘 다 단일 지점 이상치이고, sync Stage 0 표의 `†` 각주와 같은 종류
(로컬 Windows의 TIME_WAIT 소켓 잔여 상태에 따른 연결 거부 노이즈)로
본다 — 재현성 검증은 안 했다.

## 결과 표 — 컨슈머 측 지표: drain 시간

**여기가 이 실험의 핵심이다.** VU=10·INSERT만 기준으로 큐가 완전히
빌 때까지 걸린 시간(초):

| Stage(배경 데이터) | nobatch drain | batch100 drain |
| --- | ---: | ---: |
| 0 (1만) | 51s | 7s |
| 1 (30만) | **50s** | 6s |
| 2 (90만) | **60s(cap, 미완료)** | 7s |
| 3 (150만) | **60s(cap, 미완료)** | 6s |
| 4 (300만) | **60s(cap, 미완료)** | 7s |

**batch100은 Stage 0부터 4까지, 배경 데이터가 300배(1만→300만) 늘어도
drain 시간이 6~7초(INSERT만)/12~14초(INSERT+UPDATE)로 완전히
평평하다.** 이건 VU=10~500 전 구간에서 다 마찬가지다(위 raw 요약
참고) — batch100은 이 실험이 다룬 규모 범위 안에서는 데이터 크기에
사실상 영향을 안 받는다.

**nobatch는 정반대다.** Stage 0·1(배경 30만 이하)까지는 VU=10 같은
가장 가벼운 조건에서 50초 안팎으로 어떻게든 다 비웠는데, **Stage
2(90만)부터는 VU=10에서조차 60초 안에 못 비운다.** Stage 1(30만)과
Stage 2(90만) 사이 어디선가 단일 컨슈머 스레드의 초당 처리량이
Stage 0~1 수준(~200/s)에서 한 단계 더 떨어진 것으로 보인다 — 정확한
낙폭은 이 측정 방법(60초 컷오프)으로는 잴 수 없다. VU를 올릴수록
`max_queue`가 커지는 이유는 Stage 0~1 때와 같다(요청 유입은 그대로
빠른데 컨슈머가 못 따라잡아 쌓이는 것) — Stage 2~4는 여기에 더해
"기본 처리 속도 자체가 한 단계 낮아진" 효과까지 겹친다.

## Stage 4 — 동기 실험의 버퍼 풀 병목과 비교

동기 실험 [`sync/stage-4.md`](../sync/stage-4.md)는 Stage 4(300만)에서
"VU=10(사실상 무경합) 기준선 자체가 2.5배 느려짐"(8ms→21ms)을 발견했고,
`coupon_issue` 테이블+인덱스(370.7MB)가 InnoDB 버퍼 풀 기본값(128MB)을
넘어서는 시점과 정확히 일치한다고 봤다(analysis-notes.md 6장).

**비동기 batch100의 응답 지연에는 이 효과가 전혀 안 보인다** — Stage 4
VU=10 INSERT만 avg가 503µs로 Stage 0(488µs)와 사실상 같다. 그런데 이건
당연하다(위에서 설명한 대로 응답이 DB를 안 보므로). **문제는 drain
시간에도 이 효과가 안 보인다는 것**이다 — batch100 drain은 Stage
0(7s)이나 Stage 4(7s)나 똑같다. 만약 버퍼 풀 초과로 각 INSERT의 실제
DB 처리 시간이 sync에서처럼 2.5배 늘었다면, 배치 100건을 처리하는
컨슈머의 트랜잭션 시간도 늘어서 drain이 길어져야 할 텐데 그렇지
않았다.

가능한 설명 두 가지(둘 다 검증 안 됨, 다음에 볼 것):

1. **coupon_id=4(이 벤치마크 전용 쿠폰)의 인덱스 페이지가 항상
   버퍼 풀에 남아있다.** 매 VU 실행마다 `prepare-benchmark.sql`이
   coupon_id=4의 기존 행만 지우고 같은 `member_id` 범위(1~10,000
   근방)를 반복해서 재사용하므로, 이 실험을 몇 번이고 되풀이하는 동안
   그 좁은 인덱스 범위는 계속 "핫"하게 유지됐을 수 있다. 반면 동기
   실험도 정확히 같은 coupon_id=4를 쓰므로, 이 설명이 맞다면 sync가
   느려진 이유는 버퍼 풀 자체보다 **동시 커넥션 수(최대 200)가 많을 때
   생기는 잠금/래치 경합**일 가능성이 커진다 — 컨슈머는 커넥션 1개
   (스레드 1개)뿐이라 애초에 이 경합이 없다.
2. 위 nobatch의 "Stage 2부터 60초 컷오프" 결과를 보면, **DB 쪽
   병목 자체는 async에도 여전히 존재하는 것으로 보인다** — 다만
   batch100의 대량 배치 커밋(100건/트랜잭션)이 그 병목을 흡수할 만큼
   충분히 크고, nobatch(1건/트랜잭션)는 흡수 여력이 없어서 먼저
   드러났을 수 있다.

이 둘을 가리려면 nobatch의 정확한 처리량 저하폭을 재야 하는데(60초
컷오프보다 긴 관찰 시간 필요), 이번 실험 범위 밖으로 남겨둔다.

## Stage 0~4 종합 — 이 실험의 결론

1. **배치(batch100)는 이 실험이 다룬 배경 데이터 범위(1만~300만) 전체에서
   VU와도, 데이터 크기와도 거의 무관하게 안정적이다.** drain 6~7초
   (INSERT만)/12~14초(INSERT+UPDATE)로 항상 평평했고, 동기에서 나타난
   Tomcat/풀 포화나 대량 TCP 연결 거부도 없었다.
2. **배치 없는 비동기(nobatch)는 데이터가 커질수록 더 나빠진다.**
   Stage 0~1(30만 이하)까지는 그럭저럭(느리지만) 따라갔는데, Stage
   2(90만)부터는 가장 가벼운 VU=10 조건에서도 60초 안에 못 비운다.
   단일 컨슈머 스레드가 구조적 병목이라는 결론(7장·analysis-notes.md)은
   데이터가 커질수록 더 굳어진다.
3. **응답 지연(Avg/p95)만 보면 배치 유무·데이터 크기 둘 다 거의 안
   보인다** — 이 지표가 재는 건 "큐에 넣는 비용"뿐이라서다. **비동기
   시스템을 평가할 때 응답 지연만 보면 안 되는 이유**가 바로 이거다:
   컨슈머가 못 따라가고 있어도(nobatch의 60초 컷오프처럼) 클라이언트가
   받는 응답은 계속 빠르다.
4. **동기 Stage 4의 "버퍼 풀 초과로 기준선 저하" 효과가 비동기
   batch100의 drain 시간엔 재현되지 않았다** — 원인은 확정하지 못했다
   (위 "Stage 4 비교" 참고). ERD/아키텍처 결정에는 영향 없음 — 이미
   batch100이 다른 이유(TCP 거부 없음, 배치 처리량 이득)로 우세하기
   때문.
5. **최종 판단(ERD 개선 관점)**: 이 실험 범위 안에서는 **비동기 +
   배치(batch100류) 적재가 동기보다 명확히 우세**하다 — 동기가
   무너지는 VU 대역(300~500)에서 비동기는 무너지지 않고, 데이터가
   커져도(Stage 4까지) 이 우위가 유지된다. 다만 배치 없는 비동기는
   "비동기이기만 하면 낫다"는 게 틀렸다는 반례로서 값어치가 있다 —
   컨슈머 처리 능력(배치·병렬도)을 갖추지 않은 비동기는 데이터가
   커질수록 동기보다 더 빨리 무너질 수 있다.

## 아직 못 채운 것

- nobatch가 Stage 2부터 정확히 얼마나 느려졌는지 정량화 안 됨(60초
  컷오프가 관찰을 가림) — `DRAIN_TIMEOUT_SEC`을 늘리거나 컨슈머
  처리량을 직접 재는 별도 측정 필요.
- Stage 4 buffer pool 미재현의 원인(핫 인덱스 범위 vs 동시성 경합)
  확정 안 됨.
- Stage 0에서 했던 소규모 정합성 재현 테스트(요청 건수=DB 반영 건수)를
  Stage 1~4 규모로는 반복하지 않음 — 메커니즘은 Stage 0에서 이미
  확인했으므로 우선순위는 낮게 본다.
