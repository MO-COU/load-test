# Stage 0 측정 결과 (비동기 배치 적재)

배경 데이터·요청 총량 조건은 [`../sync/stage-0.md`](../sync/stage-0.md)(동기)와
동일하게 맞췄다 — `coupon_issue` 정확히 10,000건, 요청 총량 ~10,000건,
VU만 10~500으로 올린다. 차이는 API 계약뿐이다: 요청은 큐에 들어가는
즉시 `202 Accepted`를 받고, 실제 DB 반영은 별도 컨슈머 스레드가
나중에 배치로 한다(`AsyncCouponIssueConsumer`).

같은 조건으로 **두 단계**를 돌렸다 — 둘 다 컨슈머 코드는 동일하고
`BENCHMARK_BATCH_SIZE` 값만 다르다(앱을 그 값으로 재시작 후 측정):

| 단계 | `BENCHMARK_BATCH_SIZE` | 의미 |
| --- | ---: | --- |
| nobatch | 1 | 매 이벤트마다 즉시 커밋 — "요청과 DB 반영을 분리"한 효과만 측정 |
| batch100 | 100(기본값) | 최대 100건 또는 100ms 중 먼저 차는 조건으로 묶어 커밋 — 배치 효과까지 측정 |

원본 시계열: [`../raw/stage0-async-nobatch.tsv`](../raw/stage0-async-nobatch.tsv),
[`../raw/stage0-async-batch100.tsv`](../raw/stage0-async-batch100.tsv).
측정 스크립트: `scripts/large-db/run-vu-sweep-async.sh`(k6가 끝난 뒤 큐가
0이 될 때까지 최대 60초 대기(drain)한 뒤 다음 VU로 넘어간다).

## 결과 표 — 컨슈머(소비자) 측 지표: drain 시간·큐 적체·fsync

이 실험에서 가장 중요한 차이는 응답 지표가 아니라 **"큐에 쌓인 걸 실제로
DB에 다 반영하는 데 얼마나 걸렸는가"**다. k6가 끝난 시점과 실제 DB 반영이
끝난 시점(큐 크기 0) 사이의 간격이 `drain`이다.

(`max_queue` 열은 "nobatch / batch100" 순.)

`60s(cap)`은 `DRAIN_TIMEOUT_SEC=60`에 걸려 대기를 포기한 것이지 큐가
실제로 0이 됐다는 뜻이 아니다 — **nobatch는 INSERT+UPDATE 전 구간(VU
10~500)과 INSERT만 VU 200 이상에서 60초 안에 못 비웠다.** 이 경우
`fsync_delta`(그 구간 동안 실측된 fsync 증가량)는 "그 VU 단계에서 실제로
반영된 양"일 뿐 "그 VU가 만들어낸 요청량"과 다르다 — 못 비운 나머지는
다음 VU 단계가 시작된 뒤에도 백그라운드에서 계속 반영되며 다음 단계의
측정 구간을 오염시켰을 가능성이 있다(아래 3장 참고).

## 분석

### 1. 응답 지표만 보면 두 단계가 거의 똑같다 — 이게 정상이다

nobatch와 batch100의 Avg/p95/처리량은 VU별로 거의 겹친다(예: VU=500
INSERT만 p95 26.91ms vs 28.67ms). **당연한 결과다** — 응답 시점은
"큐에 넣었다"는 것만 확인하고 끝나므로, 컨슈머가 배치를 쓰는지 여부는
응답 지연에 전혀 반영되지 않는다. 배치 효과는 응답 쪽이 아니라 아래
drain·fsync 쪽에서 봐야 한다.

### 2. 배치 효과는 drain 시간에서 극명하게 갈린다

**batch100은 VU와 무관하게 drain이 항상 6~7초(INSERT만) / 11~12초
(INSERT+UPDATE)로 평평하다.** 반면 **nobatch는 VU가 오르면 drain이
같이 늘어나다 결국 60초 캡에 막힌다**(INSERT만 VU200부터, INSERT+UPDATE는
VU10부터 이미 못 비움). 이는 7장에서 세운 가설("배치는 같은 fsync
상한 안에서 실질 처리량을 올린다")을 정확히 뒷받침한다.

메커니즘은 단순하다 — 컨슈머는 **스레드 1개**뿐이다
(`AsyncCouponIssueConsumer`). `BATCH_SIZE=1`이면 이 한 스레드가 "이벤트
1건 꺼내기 → 커밋 1번(fsync 1번)"을 순차로 반복해야 하고, 이 커밋
왕복시간이 곧 스레드의 처리 상한이 된다. 실측 처리율은 INSERT만
10,000건을 49~58초에 비운 구간(VU 10~100)에서 역산하면 **초당
170~200건 정도**다. INSERT+UPDATE는 요청 1건당 이벤트 2개(INSERT +
MARK_USED)라 같은 상한에서 실질 처리량이 반 토막 나고, 그 결과 10,000
요청(이벤트 20,000개)은 어떤 VU에서도 60초 안에 못 끝낸다 — 관측과
정확히 들어맞는다.

`BATCH_SIZE=100`이면 같은 커밋 왕복 1번으로 최대 100건을 실어 나르므로
처리 상한이 이론상 ~100배 오른다. 실측 drain이 VU와 무관하게 평평한
것도 이와 일치한다 — 생산자가 얼마나 빨리 밀어 넣든, 100건 단위로 묶어
치우는 소비자가 여유 있게 따라잡는다는 뜻이다.

### 3. nobatch의 "60초 캡"은 측정 방법의 한계이지 결과가 틀렸다는 뜻이 아니다

nobatch INSERT+UPDATE는 전 VU 구간에서 drain이 60초 캡에 걸렸다. 즉
**한 VU 단계가 끝나고 다음 VU 단계로 넘어갈 때, 이전 단계의 큐 잔여
이벤트가 백그라운드에서 계속 DB에 반영되고 있었을 가능성이 있다.**
`reset_coupon4`(다음 단계 시작 전 DB 초기화)는 테이블만 초기화할 뿐 앱의
인메모리 큐(`AsyncIssueQueue`)는 건드리지 않으므로, 컨슈머는 초기화 이후
데이터에 이전 단계의 이벤트를 계속 흘려 넣었을 수 있다. 이 표의
`fsync_delta`(VU 200 이상에서 10,400~10,700대로 갑자기 낮아지고 평평해짐)가
그 정황과 맞는다 — 실제 그 VU가 발생시킨 양이 아니라 "60초 동안 컨슈머가
처리할 수 있었던 최대량"에 가깝다.

**이 실험에서 nobatch의 결론(단일 스레드·배치 없음은 구조적으로 못
따라간다) 자체는 바뀌지 않는다** — 오히려 60초 안에도 못 끝났다는 게
결론을 더 강하게 뒷받침한다. 다만 VU별 정확한 fsync 수치를 서로
비교하는 용도로는 이 표의 nobatch 열을 신뢰하지 않는다.

**추가 확인(2026-08-20): 정합성 자체는 깨지지 않는다.** 별도로 소규모
재현 테스트(nobatch 앱을 다시 띄우고 VU=20, 2,000~4,000 이벤트, 큐가
완전히 0이 될 때까지 기다림)를 돌려본 결과, INSERT만·INSERT+UPDATE
둘 다 요청 건수와 DB 반영 건수가 정확히 일치했다(유실·중복 0건,
INSERT+UPDATE는 상태도 전부 `USED`로 정확히 전이). 즉 **"60초
컷오프에 걸렸다"는 건 이 표의 fsync/큐 수치를 신뢰할 수 없다는
뜻이지, 데이터가 실제로 유실됐다는 뜻은 아니다** — 컨슈머는 느릴
뿐 결국 순서대로 다 처리한다(앱이 죽지 않는 한). 다만 실제 운영
관점에서는 "느려서 언젠가 다 처리된다"와 "60초 안에 못 끝낸다"는
여전히 다른 문제다 — 부하가 컨슈머 처리 속도보다 계속 빠르면 큐가
무한정 커지다 결국 메모리 문제로 이어질 수 있다(이 재현 테스트는
백로그가 완전히 빠질 때까지 새 부하를 안 넣었다는 조건에서만 유효).

### 4. 동기와 비교 — 애플리케이션 실패(TCP 연결 거부)가 훨씬 줄었다

[`../sync/stage-0.md`](../sync/stage-0.md)의 동기 결과와 나란히 보면:

| | 동기 | 비동기(nobatch/batch100) |
| --- | --- | --- |
| VU=200 상태 | Tomcat 스레드 200/200 포화, `hikari_pending` 144~149 | 포화 없음(스레드가 DB를 안 기다림) |
| VU=500 INSERT+UPDATE 실패율 | **24.11%**(TCP 연결 거부) | 0.49% / 0.25% |
| VU=500 INSERT만 실패율 | 2.78% | 6.29% / 3.94% |

INSERT+UPDATE 기준으로는 예상대로 실패율이 크게 줄었다(24.11% →
0.5% 이하) — 요청 스레드가 DB 응답을 기다리지 않으니 Tomcat 스레드
포화 자체가 없어진 결과다. **다만 INSERT만은 오히려 동기(2.78%)보다
비동기(6.29%/3.94%)가 높게 나왔다** — 두 값 다 한 자릿수 %대라 큰
의미를 부여하긴 이르지만, k6 로그를 보면 실패 유형은 동기와 동일하게
"TCP 연결 거부"(`connectex: ... actively refused`)다. 큐 자체는
무제한(unbounded)이라 큐가 가득 차서 거부한 게 아니라, 순간적으로
몰리는 신규 연결 수(VU 500)를 OS/Tomcat accept 큐가 짧게 못 받아준
것으로 보인다 — 로컬 Windows 환경의 노이즈일 가능성이 있어(동기
Stage 0 표의 `†` 주석과 같은 종류) 단정하지 않는다.
