# Atomic Update 실험 결과

## 테스트 방식

`load-test/rush.js`는 쿠폰 1번에 발급 요청을 반복 전송한다. Atomic Update는 재고가 남아 있을 때만
`issued_count`를 증가시키는 조건부 UPDATE로 재고 확인과 차감을 하나의 DB 연산으로 처리한다.

| 항목 | 설정 | 의미 |
|---|---:|---|
| 쿠폰 재고 | 1,000장 | 성공 발급의 상한 |
| 가상 사용자 | 최대 2,000 VU | 60초 동안 0명에서 2,000명까지 증가하는 동시 요청 부하 |
| 회원 ID | 1~2,000 무작위 | 같은 회원의 재시도를 포함해 중복 발급 방어를 함께 검증 |
| 테스트 시간 | 60초 | 부하를 발생시킨 시간. 종료 후 진행 중 요청은 최대 30초 동안 마무리 |
| 요청 대상 | `POST /issue?couponId=1&memberId={1..2000}` | 쿠폰 1번 발급 API |

> VU 2,000은 60초 내내 2,000명이 고정 접속했다는 뜻이 아니다. 0명에서 점진적으로 늘어나며,
> 실행 중 관측된 최대치는 1,995 VU였다.

## 핵심 결과

| 관찰값 | 결과 | 해석 |
|---|---:|---|
| 전체 요청 | 61,372건 | 약 60초 동안 발급 API에 집중 요청이 들어왔다. |
| 정상 발급 (`200`) | 1,000건 | 쿠폰 재고 1,000장과 정확히 같다. 요청 응답 기준으로 초과 발급 징후가 없었다. |
| 중복 차단 (`409 DUPLICATED`) | 358건 | 같은 회원의 재시도 358건을 발급으로 처리하지 않고 중복으로 차단했다. |
| 품절 응답 (`409 SOLD_OUT`) | 60,014건 | 1,000장 소진 뒤 이어진 요청은 추가 발급 없이 품절로 응답했다. |
| 예상 밖 오류 (`errors`) | 0건 | 5xx·400·404 등 예상하지 않은 응답이 없었다. |
| HTTP 실패율 | 0.00% (0 / 61,372) | `200`, `409` 이외의 HTTP 실패가 발생하지 않았다. |

## 사용자 대기 시간과 처리량

| 지표 | 결과 | 사용자 관점 해석 |
|---|---:|---|
| 평균 응답 시간 | 약 1.00초 | 발급 성공·중복·품절을 포함한 모든 요청이 평균 약 1초 후 응답받았다. 정상 발급 요청만의 평균 시간은 아니다. |
| p90 응답 시간 | 1.75초 | 요청 100건 중 약 90건은 1.75초 이내에 응답받았다. |
| p95 응답 시간 | 1.85초 | 느린 쪽 5%를 제외한 요청 95%는 1.85초 이내에 응답받았다. 사용자가 길게 기다린 경우도 대체로 2초 안쪽이었다. |
| 최대 응답 시간 | 2.29초 | 이번 실행에서 가장 오래 걸린 요청의 응답 시간이다. |
| 처리량 | 약 991 req/s | 이 PC에서 애플리케이션과 k6를 함께 실행한 조건의 참고 처리량이다. 다른 PC 결과와 절대값으로 비교하면 안 된다. |

## 판정

| 기준 | k6 결과 기준 판정 | 최종 확인 방법 |
|---|---|---|
| 초과 발급 없음 | 성공 발급 1,000건 = 재고 1,000장 | `verify.sql`에서 `issued_count`와 `issued_rows`가 모두 1,000인지 확인 |
| 중복 발급 없음 | 중복 시도 358건은 모두 `DUPLICATED`로 응답 | `verify.sql`의 회원별 중복 행 조회 결과가 비어 있는지 확인 |
| 서버 오류 없음 | `errors` 0건, HTTP 실패 0건 | k6 `errors` 임계값(`count==0`) 통과 |

실행 직후에는 아래 명령으로 DB의 최종 상태도 함께 기록한다.

```bash
docker compose exec -T mysql mysql -ucoupon -pcoupon1234 coupon -e "source /scripts/verify.sql"
```
